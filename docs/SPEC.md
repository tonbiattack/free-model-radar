# Free Model Radar — 仕様書

## 1. 目的

OpenCodeなどのコーディングエージェントから利用できる、無料枠のあるLLM APIを探し、実用性を比較し、導入設定を簡単に生成できる静的Webサービス。**無料で呼び出せる**ことと**エージェントとして正常に動く**ことを明確に区別する。

## 2. 基本方針

- 静的サイトをGitHub Pagesで公開。閲覧・検索・設定生成は無料、ログイン不要。
- データはGit管理のJSON/YAMLで保持し、ビルド時検証して配信。データベースや有料APIを必須にしない。
- 既存の ai-plan-radar はサービスの料金プラン比較、本プロジェクトは「無料API・モデルのOpenCode実用性」に特化。
- 調査結果の**出典URL・確認日時・確認手段**を表示。未確認情報は推測で埋めず「不明」とする。
- 無料枠は「恒久無料 / 期間限定トライアル / 初回クレジット / 条件付き / 終了・停止 / 不明」を区別。
- 無料という言葉にはAPI利用そのものが無料であることを要求し、モデルの重みが公開されているだけでは対象にしない。
- 初期実装の焦点は OpenCode。将来、他のOpenAI互換クライアントへ拡張可能なデータモデルを使う。

## 3. 想定ユーザーと利用シナリオ

1. OpenCodeで課金なしに使えるプロバイダーを見つけたい。
2. ツール呼び出し、長い作業、コンテキスト長、制限値からエージェント向きのモデルを選びたい。
3. APIキーを自分で取得し、OpenCodeの設定例をコピーして接続したい。
4. 無料枠の追加、縮小、終了、モデル変更を素早く把握したい。

## 4. 画面・機能

### 4.1 モデル一覧（MVP）

- 同一モデルは 1 件にまとめて表示し、提供元の数を示す。同じモデルを複数の提供元が扱う場合は重複カードにしない。
- プロバイダー・モデル名・無料枠種別・認証要件・RPM/RPD/TPM等・ツール呼び出し対応・確認日時・検証状態を表示。
- 絞り込み: 恒久無料のみ、ツール呼び出し対応、クレカ不要、登録の手間、OpenCode動作確認済み、複数の提供元がある、プロバイダー、情報鮮度。
- 検索: モデル名・別名・開発元・APIのモデルID・プロバイダー名。モデル名とサービス名の両方から見つかる。
- ソート: 最終確認日、提供元の数、制限の充実度（同一単位で比較できるときのみ）、モデル名。
- 各モデルから公式の料金表・ドキュメント・APIキー取得ページを開ける。
- 未確認値を0や「非対応」と表示しない。UNKNOWN / YES / NO を区別。

### 4.2 詳細ページ（MVP）

- 第一階層: モデル本体の情報と「このモデルを無料で使える提供元」の比較表。
- 比較表の列: 提供元、無料枠種別、RPM/RPD/TPM と適用範囲、カード要否、登録の手間、ツール呼び出し、検証状態、確認日時。
- 第二階層: 提供元を選ぶと、その提供元の条件・導入手順・OpenCode 設定生成へ遷移する。

- モデルID、APIベースURL（公開可能なもの）、API形式（OpenAI互換等）、コンテキスト長（出典付き）、レート制限・総量制限、無料枠の継続条件、利用規約の注意事項。
- 対応機能: tool calling、streaming、JSON mode、reasoning（それぞれ公式記載と実機検証の区別）。
- 確認結果: 公式記載、接続検証成功/失敗/未実施、検証日、検証バージョン。
- 性能は自前評価せず、出典のある比較ページへリンクする。
- 出典および更新履歴へリンク。

### 4.3 OpenCode設定ジェネレーター（MVP）

- 選択したプロバイダーとモデルに対して現行OpenCode仕様に準拠した `opencode.json` の設定例を生成・コピー。
- OpenCodeネイティブ対応の場合は既存プロバイダーの設定方法を優先し、独自プロバイダーは必要な項目だけを出力。
- APIキーの入力・収集・送信・保存は行わない。プレースホルダーと環境変数利用の説明を表示する。
- ネイティブ対応・OpenAI互換で設定形式が違う場合は分岐する。
- 生成設定は実在プロバイダーで動作確認。未検証の場合は「未検証」と明示。
- 設定コピー前に表示内容を確認できる。

### 4.4 更新情報（Phase 2）

- 新規モデル、新規無料枠、制限変更、無料枠終了を変更履歴として表示。
- 変更時刻と発見時刻は別管理。元情報を追跡できる差分を保存。
- 重大変更は目立たせるが、未確認の自動検知だけで「終了確定」としない。

## 5. 収集・検証

### 5.1 データ取得

- まず公式ドキュメント/料金ページを一次ソースとする。コミュニティ投稿は候補発見に利用できるが、公式未確認のまま確定値にしない。
- GitHub Actions scheduled workflow で定期的に変更確認。ワークフローは手動実行にも対応。
- サイト更新のためにLLM有料API、スクレイピング代行、有料DBは使わない。
- robots.txt、利用規約、レート制限に従う。アクセス不可のページは人手確認のキューに残す。
- 取得失敗と「サービス終了」を区別し、連続失敗や一時的障害で掲載内容を自動削除しない。
- 自動検知内容はPR（または検証用アーティファクト）として差分を確認してから公開。安全な既知パターンのみ自動適用する設計も可。

### 5.2 動作検証（Phase 2）

- 公式仕様と別に、接続可否・tool calling（関数を要求し結果を返す）・streaming・OpenCode経由の簡単なタスクを評価。
- 検証には提供者の許可・無料枠範囲・コスト上限を厳守。利用者のAPIキーを収集しない。
- 有効な検証用キーがない場合はスキップして「未検証」とする。
- 単発成功だけで長時間エージェント利用を保証しない。
- 検証に費用が生じる場合は自動実行しない。

## 6. データモデル（概念）

- **CanonicalModel**: id, name, developer, family, aliases — モデル本体。提供元をまたぐ同一性の基準
- Provider: id, name, website_url, docs_url, signup_url, api_format, base_url, native_opencode, authentication, credit_card_required（nullable）, signup_friction
- Model: id, provider_id, **canonical_id**, display_name, model_id, context_tokens（nullable）, capabilities（各3値）, status
- FreeTier: type, available, reqs, rpm/rpd/tpm/tpd（nullable）, monthly_quota（nullable）, concurrency（nullable）, expiration, caveats
- Evidence: field, value, source_url, source_type（official/community/test）, observed_at, checked_at, confidence
- Verification: method, status（passed/failed/untested/unknown）, tested_at, opencode_version, notes
- PerformanceRef: benchmark, url, as, note — 性能は自前評価せず出典へリンク
- ChangeLog: entity_id, field, previous, current, detected_at, effective_at（nullable）, evidence_url, review_status

**数値制限はプロバイダー単位・モデル単位・アカウント単位が混在し得るため scope と期間単位を保持する。** 0 と null を区別。IDはURLなどに依存せず安定化する。

**同一モデルの判定は canonical_id で行う。** 表示名や API のモデル ID は提供元ごとに表記が異なるため、文字列一致では同一性を判定しない。一覧は canonical model 単位でまとめ、詳細で提供元を横断比較する。単位・適用範囲の異なる制限を単純な数値ランキングにしない。

## 7. 技術構成（推奨）

- フロントエンド: TypeScript + Vite + React（または軽量静的サイト構成）。UIの技術選択は初期Issueで確定。
- 公開: GitHub Pages、クライアントサイド検索/絞り込み。
- データ: repository/data/ 配下のJSONまたはYAML、JSON Schema / Zod 等で型・整合性検証。
- 自動化: GitHub Actionsで定期収集・検証・ビルド・デプロイ。外部の有料サービスは不要。
- テスト: データスキーマ、フィルタ、設定生成、ビルド、重要なUI、翻訳キーの欠落を自動テスト。
- セキュリティ: シークレットはコミットしない。公開Webサイト上でAPIキーの取り扱いを行わない。

## 7.1 多言語（i18n）

英語を既定、日本語も維持する。**翻訳によってデータ更新コストを倍増させない**ことを制約とする。

- URL は `/:locale/...`（`en` / `ja`）。接頭辞なしのアクセスは既定言語へ誘導する。
- 事実データ（モデルID、提供元ID、数値、URL、日付）は言語非依存で1つだけ持つ。
- 説明文は `data/i18n/en.json` に、原文の内容ハッシュをキーとして訳を保存する。原文を変えるとキーが変わり、未翻訳として検出される。
- UI文言は `src/lib/messages.ts` に日英で持つ。日英のキー集合が一致することをテストで検証する。
- `html lang`、title、meta description、canonical、hreflang、OGP、sitemap はロケール単位で生成する。
- 状態語（不明 / 未検証 / 終了）は日英で意味を対応させ、誤訳による断定を防ぐ。「不明」と「非対応」を同一視しない。

言語を追加する手順:

1. `src/lib/locale.ts` の `locales` に追加する
2. `src/lib/messages.ts` に同じキー集合のカタログを追加する
3. `scripts/translations.ts` に対応する訳を追加し、`npm run i18n:build` を実行する
4. `scripts/prerender.ts` と `scripts/sitemap.ts` の `LOCALES` に追加する
5. `npm test` と `npm run build` が通ることを確認する

## 8. 非機能要件

- スマホ・PC対応、ダークモード、キーボード操作、コピーボタンの成功フィードバック。
- 初回表示が軽量で、無料枠情報を検索エンジンと共有URLから見つけられる。
- 最終確認日時が古いデータは注意表示。監視失敗時も直近の有効データを配信。
- 出典が消滅しても過去の履歴に存在を残す。
- 可能ならOSSとしてデータ追加PRを受け付け、テンプレートとバリデーションを用意。

## 9. MVPの完了条件

- 少なくとも5プロバイダーの実際の無料API情報（公式出典・確認日時つき）を掲載。
- フィルタ/検索/詳細/設定生成が利用でき、設定例のコピーができる。
- 恒久無料とトライアルを混同せず、機能の不明値を誤表示しない。
- 1モデルを複数の提供元が扱うデータで、モデルが重複せず比較でき、提供元ごとの違いを正しく表示できる。
- GitHub Pagesで無料公開し、GitHub Actionsでビルドとデータ検証が成功。
- READMEに目的、開発・デプロイ方法、情報の鮮度と免責、コントリビューション方法を記載。

## 10. 初期スコープ外

- APIキーを預かる代理実行、ユーザーアカウント、課金、独自推論API、プロバイダー規約に反する自動登録。
- 全プロバイダーのリアルタイム接続保証、ベンチマークの独自大規模実施。
- 無料枠を使い切らないようにするための複数アカウント自動切替。

## 11. 実装優先順位

P0: プロジェクト基盤 → スキーマ/初期データ → 一覧/比較 → 詳細 → 設定生成 → GitHub Pages公開
P1: 定期検知/変更履歴 → エージェント適性の実機検証 → コミュニティ更新ワークフロー
